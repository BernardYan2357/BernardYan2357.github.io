# 如何用 AI 写代码

References: [我的 AI 编程全流程：如何使用 AI 稳定交付一个高质量的产品](https://www.bilibili.com/video/BV154426xEha)

## **问题引入**

你可能会想：装个 Codex，直接给 AI 发条指令——"给我做个笔记软件/剪辑软件/电子书阅读器"，不就行了吗？

但问题是：

- AI 做出来的效果真的跟你预期的一样吗？
- 有没有可能你脑子里想的是一个东西，AI 最后交付的完全是另外一个东西？
- 更不用说有些时候 AI 做出来的产品还有很多 bug，跟自己想象的效果相差甚远。

核心问题：怎么才能让 AI 交付一个真正让你满意的作品？

## **挑选 Coding Agent**

目前主流的编程 Agent ：

- Codex：推荐，功能相对完善，几乎没有明显短板；
- Claude Code：主流选项之一；
- OpenCode、Pi、Cursor 等。

## **环境搭建**

### **创建项目文件夹并初始化项目**

1. 为产品创建对应的文件夹（示例项目命名为"马克阅读"——一个电子书阅读器）
2. 打开 Codex → 点击加号创建新项目 → 项目类型选"本地"
3. 把刚创建的文件夹加入项目 → 创建

### **初始化 Git 仓库**

### **创建 AGENTS.md 项目说明书**

AGENTS.md 的作用：给 Codex 写的项目说明书。每次开启新的会话，Codex 会优先读取里面的内容，快速了解项目背景和开发规范。

写入两条规定：

1. 每次改动后必须创建对应的 Git commit——便于后续追踪和回滚。相当于 AI 每完成一个功能都顺手保存一个版本快照，改坏了可以直接退回正常版本，不用担心代码越改越乱。
2. 每次改动后必须编写或更新相关测试，并在交付前确保所有测试和验收全部通过——不让 AI 写完代码就直接交差，而是自己先跑一遍测一遍，发现问题继续修，基本确认没问题再来汇报。可以提前挡掉很多明显的 bug，节省人的时间。

## **产品方案设计**

### **与 AI 讨论产品边界（MVP 策略）**

启动指令示例：
>我想做一个电子书阅读器，打算先从 MVP 版本开始，你觉得这一版做哪些功能比较合适呢？

> MVP（Minimal Viable Product，最小可行产品）：第一版只做最核心、最必要的功能，先把主流程跑通，其他功能以后慢慢加。好处是用较低成本快速验证产品方向，避免一开始功能铺太大、方向错了导致大量返工。

视频中逐步砍需求的对话技巧——看 AI 的完整回答后，把所有意见追加到输入框里一次性提交：

- ❌ 砍掉 EPUB 导入："EPUB 稍微有些复杂，一开始是不是可以只支持最简单的 TXT 文本文件？"
- ❌ 砍掉目录/章节："只做 TXT 的话就没有目录和章节可言了，TXT 没有目录和章节的概念，这些也不用做了。"
- ❌ 砍掉多主题："只做明亮主题就行，护眼和深色可以先不做。"
- ❌ 砍掉书签："书签也可以先不做，不是必要功能。"
- ✅ 总结表态："总之我们先做最基本的功能，其余的后面再迭代，你觉得前面这些想法有没有什么问题？"

### **整理产品设计文档**

指令：
> 我同意你的建议。接下来帮我整理一份产品设计文档吧，不用太详细，把整体方向和主要功能梳理出来就可以。

措辞要点：明确说"不用太详细"——字太多看着累，只需保证大方向和自己的预期一致；细节不符后面再迭代即可。

### **（可选）做一个前端 Demo**

Demo 指令模板：
> 帮我做一个 demo，不用实现真实的后端功能，数据模拟一下就行，我主要是想看看整体界面和操作流程是否合理。

Demo 是什么：一个可以实际操作的前端页面。只有前端是真的，后端逻辑不实现、数据用模拟的。

目的：让用户体验整个界面的交互流程顺不顺手，不对就让 AI 改，直到符合预期。

做 Demo 的两个好处：

1. 提前验证产品设计——很多东西光靠文字难以想象，把页面画出来亲自操作，才能发现之前没想到的问题；发现设计不合理就改 Demo，同步调整产品设计文档。
2. 让产品实现更精确——Demo 能非常直观地告诉 AI"我最终想要的产品大概就是这个样子"，这是文字描述很难做到的。实现时把设计文档 + Demo 一起交给 AI，做出来的一般更接近预期。

要不要做 Demo 的判断标准：后端实现成本。

- 后端成本高（如个人知识库，涉及文档处理、搜索检索策略、模型调用等大量后端逻辑）→ 值得先做 Demo，先把界面和交互定下来
- 后端成本低（如本例的电子书阅读器，导入 TXT 就行，没什么复杂逻辑）→ 没必要专门做 Demo，属于重复劳动；直接把产品做出来，跑起来后哪里不顺手直接在完整产品上调整

## **技术方案设计**

### **会话选择：新开 vs 继续**

- 可以在当前会话继续追问，也可以新开会话做技术方案
- 担心长上下文影响效果？现在的顶级模型对长上下文的驾驭能力越来越强，再加上对应的上下文压缩机制，正常使用一般不用过于担心
- 为稳妥起见、让技术方案讨论更聚焦，建议新开一个会话专门做技术方案

### **与 AI 探讨技术选型**

指令：
> 在这个目录下面有一份产品设计文档，请你读一遍，然后告诉我用什么技术栈设计这个产品比较合适。不用给出过于详细的设计，我们就先探讨一下。我听说 Electron 还可以，你怎么看？

AI 回答：Electron 非常合适、优先采用，给出建议技术栈，同时说明 Electron 的缺点和另一个备选方案 Tauri。最终确定：

> Electron + React + TypeScript + Vite + Electron Forge

### **输出技术方案文档**

指令：
> 行，就按你说的来。现在请你写一个技术方案，放在 docs 文件夹里面。

后面写代码时就可以以这个文档作为参考。不是特别懂这块也没关系，保证大方向没问题就行。

## **产品实现与人工验证**

### **给 AI 自测能力（安装插件）**

写代码前，最好让 AI 拥有自行验证结果的能力。Codex 建议至少安装两个插件：

- Computer Use：操作电脑
- Chrome：查看 Chrome 页面

有了这两个插件，大部分功能都可以交给 AI 验证（包括电子书阅读器这类产品）。用其他编程 Agent 的，可自行查找对应插件或 Skill。

> 给 AI 一个能验证的环境非常重要。否则 AI 很容易写出一堆 bug——它没法验证；就像人写代码没法验证一样，估计也会有一堆 bug。

### **让 AI 实现产品**

指令：

> 这个目录下面有两个文档：一个是产品设计，一个是对应的技术方案。请你读一下这些文档，然后根据里面的要求实现这个产品。提交。

结果：AI 不仅把产品做完了，还完成了各种自测，确保代码没有问题——这正符合 AGENTS.md 中的要求（第二条：每次改动后必须编写或更新相关测试，并在交付前确保所有测试和验收全部通过）。

> 注意：自测只能尽量提高代码可靠性、提前发现明显问题，并不能保证交付的产品一定没有 bug。真正用起来怎么样，还得自己亲自验证。

### **人工验证与修复**

1. 按 AI 提示执行 npm start 启动
2. 上来就报错："操作失败，请稍后重试"——AI 确实不是 100% 靠谱，即使它能自测也未必完全可靠
3. 让 AI 修复：_打开之后直接显示了一个报错"操作失败，请稍后重试"，请修一下_
4. 修好后再次启动，错误消失，导入一本 TXT 文件测试，一切正常 → MVP 完成

## 总结

### **取舍逻辑：参与的深度 = 对结果的掌控力**

- 不做产品设计：如果不在意产品怎么设计，功能能用就行 → 交给 AI，问题不大，只是把更多决策权交给 AI，掌控更少
- 不做技术设计：不关心代码怎么实现 → 让 AI 自己决定，同样可行
- 核心权衡：
    - 参与得越多 → 对结果把控越强，但投入的时间精力越多
    - 参与得越少 → 开发更省事更快，但结果与预期出现偏差的可能性越高

### **个人判断标准：按需求的复杂度和重要性**

- **简单且不重要**：忽略产品设计和技术设计两个环节，搭好环境直接让 AI 实现，验证完即结束，流程非常快
- **复杂且重要**：参与产品设计和技术设计环节，走完完整五步，尽可能保证最终产品质量

> 没有固定标准，本质上是在开发效率和结果可控性之间做取舍。

### **三个不能省的原则**

**原则 1：必须有版本管理工具**

- 用 Git 管理代码
- AI 写代码不可能每次都完全正确，甚至会在修改过程中把原本正常的功能改坏
- 用 Git 后，每完成一个功能都保存一个对应的版本，出了问题能很方便地回退到之前正常的状态
- 条件允许的话，把代码同步到 GitHub 之类的远端仓库，本地丢了也能从远端恢复

**原则 2：必须给 AI 自测的能力**

- 很多人只让 AI 写代码，但不给它验证的环境，结果自己沦为"测试员"，来回帮 AI 找 bug，极其浪费时间
- 应该把相关工具和插件开放给 AI，让它自己写完自己测，这样交付出来的代码质量会高很多

**原则 3：必须进行人工验证**

- AI 自测再充分，也不可能覆盖所有问题
- 交互体验、不容易想到的边界情况，都很容易被漏掉
- 产品到底好不好用、是不是我们真正想要的，最终还是要自己试一遍才知道

> 总结：真正不能省的就三件事——用 Git 搭好环境、让 AI 具备自测能力、最后一定要人工验证。产品设计和技术设计要做得多细，看情况决定。

## **结语**

这套流程只是现阶段探索出来的比较合理的方法，并不是唯一的标准答案。随着大模型能力的不断进化，AI 编程的模式肯定还会变化，需持续尝试其他可行方案。
